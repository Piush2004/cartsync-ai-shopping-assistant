# Canonical Architecture Decision

Date: 2026-08-11
Status: Decided
Author: Claude Code (primary engineering agent), following on from `CARTSYNC_QA_FINAL_REPORT.md`

## 1. Decision

**`apps/api` (FastAPI + SQLAlchemy + Alembic + SQLite) and `apps/web` (Next.js) are the
canonical CartSync architecture.**

Everything at the repo root — `src/`, `python/`, `frontend/`, `functions/`, `local-compute/`,
and the root Firebase config (`firebase.json`, `firestore.rules`, `firestore.indexes.json`,
`storage.rules`, `.firebaserc`) — is a disconnected, abandoned prototype tree. It shares no
auth system, no database, and no request path with `apps/*`. It should be **archived**, not
deleted outright, because a small number of ideas inside it (below) are worth referencing when
real CV work starts. The root `README.md` currently describes the *legacy* tree as if it were
the current product — that is the single most misleading piece of documentation in the repo
and is corrected as part of this decision (§5).

This decision does not by itself make real camera measurement exist. It closes the "which
codebase are we building on" question so that work can proceed without ambiguity.

## 2. How this was determined

Full investigation (file-by-file, with line numbers and reproduction steps) was performed by
a read-only audit agent; the complete findings are preserved in the agent transcript for this
session. Verified independently for this doc:

- `apps/api/routers/measurement.py:28-44` — `/measurement/extract` is confirmed still
  hardcoding `confidence_score=0.92` and falling back to `random.uniform(-2, 2)` jitter on a
  fixed baseline when `raw_data` omits a field. It only accepts already-known numeric values
  (manual entry) — no image ever reaches this endpoint (BUG-01 already removed the camera→API
  call that used to imply otherwise).
- `apps/web/src/lib/cv/` contains exactly 6 files: `vision/types.ts`, `vision/interfaces.ts`,
  `quality/blur.ts`, `quality/lighting.ts`, `quality/validation.ts`,
  `camera/state-machine.ts` — type interfaces, image-quality heuristics, and a state machine.
  No `VisionProvider` implementation exists.
- `docs/` at the repo root (`ARCHITECTURE.md`, `AI_MEASUREMENT_PIPELINE.md`,
  `SIZE_RECOMMENDATION_ENGINE.md`, `DATASET.md`) all describe the legacy `python/`/
  `local-compute/` design, not `apps/api`.

to demonstrate the structure"* — the number was never computed from a real run.

## 3. What is reusable (concepts, not files)

Nothing should be copied wholesale — every pipeline file assumes Firestore/Firebase plumbing
that doesn't exist in `apps/api`, and the CV "hard parts" are stubbed throughout. Four ideas
are worth keeping as reference when Phase 6+ (real CV implementation) begins:

1. **Height-based monocular calibration strategy** — `docs/AI_MEASUREMENT_PIPELINE.md` (lines
   ~267-394) and `local-compute/services/height_calibration.py` (26 lines): derive
   `cm_per_pixel` from known user height vs. detected pixel height (nose/eye-line → ankle),
   with documented limitations around camera tilt/distance. No reference object needed. This
   matches the master prompt's Phase 8 recommendation to start with user-height calibration.
2. **MediaPipe pose validation logic** — `local-compute/services/pose_detection.py`:
   visibility thresholds and front/side view-ratio sanity checks on real landmark coordinates.
   Small, real, and portable.
3. **Ellipse-based circumference formula** — the Ramanujan ellipse-perimeter approximation used
   identically in `local-compute/services/measurement_calculator.py` and
   `python/pipeline/measurement.py`. Standard technique for width→circumference estimation,
   framework-agnostic.
4. **Measurement-definition-as-YAML pattern** — `python/measurement_definitions/*.yaml` +
   `FormulaRegistry` — a clean, declarative way to define per-measurement formulas.

## 4. What is obsolete / to archive

Everything else in the legacy tree, specifically:

- All depth-estimation code (`local-compute/depth/`, `python/pipeline/depth.py`,
  `src/lib/intelligence/measurement/depth.ts`) — every implementation is a hardcoded-constant
  stub or depends on model weights absent from the repo.
- All SMPL/avatar-mesh code (`local-compute/avatar/`) — no real model files; explicit
  emulated-mesh fallback.
- `functions/src/services/measurements/poseDetection.ts` — self-admitted mock.
- `python/pipeline/` as a whole — non-importable, and even fixed, assumes Firestore/Storage
  plumbing that doesn't apply to `apps/api`.
- The three parallel frontend apps (`src/`, `frontend/`) — redundant with `apps/web`; `src/`
  is already excluded from the npm workspace build graph.
- `local-compute/`'s trained ML artifacts (`models/ml/*.pkl`) and any accuracy numbers derived
  from them — trained on synthetic Gaussian-noise data, not meaningful, must not be cited.
- Root Firebase config (`firebase.json`, `firestore.rules`, `firestore.indexes.json`,
  `storage.rules`, `.firebaserc`).

## 5. Migration / archival plan

Chosen approach: **move, don't delete**, so the reference material in §3 stays retrievable
without cluttering the active workspace or misleading new contributors.

1. Create `archive/legacy-firebase-stack/` at the repo root.
2. `git mv src python frontend functions local-compute archive/legacy-firebase-stack/`
   (preserves history for whoever wants to dig later — there is only one commit today, but
   this keeps the convention correct going forward).
3. `git mv firebase.json firestore.rules firestore.indexes.json storage.rules .firebaserc archive/legacy-firebase-stack/`
4. Add `archive/legacy-firebase-stack/README.md` pointing back to this document and listing
   the four reusable ideas in §3 with their exact paths.
5. Rewrite the root `README.md` to describe `apps/api` + `apps/web` as they actually are today
   (FastAPI/SQLAlchemy/SQLite backend, Next.js frontend, no working camera measurement engine
   yet) instead of the aspirational Firebase/MediaPipe/Depth-Anything-V2 description that
   currently matches the archived tree, not the active one.
6. Remove `src`, `python`, `frontend`, `functions`, `local-compute` from any tooling that
   might implicitly touch them (none currently reference them from `apps/*` or root
   `package.json`, so no build config changes are expected — verify after the move).

This step is a large, somewhat irreversible-feeling filesystem move (~27,000 lines across 6
locations) touching the repo root. **It has not been executed yet** — it's queued as the
first item of the stabilization backlog and will be run as its own isolated change so it can
be reviewed/reverted independently of any other work.

## 6. Non-decision: real CV implementation

This document decides *where new CV code will live* (`apps/web/src/lib/cv/` behind the
existing `VisionProvider` interface, plus whatever `apps/api` endpoints are needed for
server-side steps) — it does not implement it. Per the legacy audit, no existing depth
estimation or 3D body modeling in this repo is trustworthy enough to port as-is; a real
pipeline still needs to be built essentially from scratch, informed by §3's four salvageable
concepts. That work is tracked separately (see the stabilization backlog).
